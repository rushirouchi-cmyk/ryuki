# 判断記録 (ADR)

要件で明示されていなかった箇所について、人材紹介業・BtoB SaaS・ATS/CRM の一般的な実務にもとづいて置いた仮定を記録する。いずれも変更可能な判断であり、実運用の中で見直す前提とする。

---

## ADR-001: 認証は自前実装（外部 IdP に依存しない）

**背景**: 「安全な認証方式」とのみ指定されていた。

**判断**: bcrypt によるパスワードハッシュ + HMAC 署名付き JWT を httpOnly Cookie で保持する方式を自前で実装した。NextAuth 等のライブラリは使っていない。

**理由**: 社内業務システムで利用者数が限られ、当面は外部 IdP との連携要件がない。依存を減らすことで、将来 Google Workspace SSO 等へ移行する際に差し替え箇所が `src/lib/auth.ts` に閉じる。

**トレードオフ**: パスワードリセット・MFA・ソーシャルログインは未実装。必要になった時点でライブラリ導入を検討する。

---

## ADR-002: 開発既定は SQLite、本番は PostgreSQL

**背景**: 技術要件では PostgreSQL が推奨されていた。一方で「外部サービス未接続でも開発を止めない」ことも要求されていた。

**判断**: Prisma スキーマの `provider` を切り替え可能にし、開発既定を SQLite にした。切り替えは `npm run db:use-postgres` の 1 コマンド。

**理由**: `git clone` 直後に DB サーバーを立てずに `npm run db:reset && npm run dev` で全機能を確認できることを優先した。本番は PostgreSQL を想定している。

**制約**: 両者で同一スキーマを動かすため、Prisma の `enum` と scalar list を使わない。

- 列挙値は String 列とし、意味づけは `src/lib/domain/enums.ts` に集約する
- 配列・構造化データは JSON 文字列として String 列に保存し、`src/lib/json.ts` 経由で読み書きする

**副次的な利点**: 列挙値の追加が DB マイグレーションを伴わない。

## ADR-003: `npm run db:reset` は SQLite 専用

**背景**: `prisma db push --force-reset` は接続先の全データを破壊する。

**判断**: `--force-reset` を使わず、ローカルの SQLite ファイルを削除してからスキーマを適用する方式にした。`DATABASE_URL` が `file:` で始まらない場合はエラーで停止する。

**理由**: 誤って本番 PostgreSQL に対して実行された場合の被害が回復不能なため。PostgreSQL のリセットは、対象が開発 DB であることを確認したうえで手動実行する運用とする。

## ADR-004: Level 3（重大）の条件を限定する

**背景**: 要件では Level 3 の例として「内定者フォロー遅延 / 応募意思ありなのに推薦未実施 / 面接前なのに対策未実施 / CA へのAI確認にも回答なし / 重要候補者を複数日放置」が挙げられていた。「複数日」の定義と、他のアラートが重大へ昇格する条件は未定義だった。

**判断**:

- ルール自体が Level 3 のもの（内定者フォロー / 推薦未実施 / 面接対策未実施）
- CA が AI 確認に回答しないままエスカレーション時間を超過した場合
- **S または A ランクの候補者について、期限を 72 時間以上超過した場合**

以上に限定し、それ以外は超過してもレベルを昇格させない。

**理由**: 当初は「SLA の 2 倍超過で 1 段階昇格」としたところ、デモデータ 12 名で 22 件中 17 件が重大となり、優先順位が機能しなくなった。重大を絞ることで、経営者への即時通知が本当に重要なものだけになる。

**現状**: 同条件で重大は 5 件（全 22 件中）。

## ADR-005: 過去実績は当面 Match Score に反映しない

**背景**: 「類似候補者の過去実績を Match Score にも将来的に反映できる設計とする。初期データが少ない段階では、ルールベースを優先する」とされていた。

**判断**:

- 類似の定義: **同一の主職種 かつ 総経験年数 ±3 年**
- 母数が **5 件未満**の場合は統計を表示せず「参考値」と明示する
- いずれの場合も Match Score には加算しない。参考情報として併記するのみ

**理由**: 十数件のデータで算出した通過率をスコアに混ぜると、少数の偶然が判断を歪める。データが一定量たまり、有意性を確認してから反映する。

**将来**: `src/lib/domain/knowledge.ts` の `similarCandidateOutcomes()` が返す統計を、`matching.ts` の要素として加算する形で拡張できる。

## ADR-006: 営業日は土日のみ除外（祝日カレンダー未対応）

**背景**: SLA に「翌営業日まで」という指定があった。

**判断**: `isBusinessDay()` は土日のみを非営業日として扱う。日本の祝日は未対応。

**理由**: 祝日カレンダーの管理（毎年の更新、会社独自の休業日）は運用負荷を伴う。まず土日対応で運用し、必要性が確認できてから設定テーブルとして追加する。

**影響**: 祝日を挟む「翌営業日」判定が 1 日早まる。安全側（早めにアラートが出る）に振れるため、見逃しは発生しない。

## ADR-007: 資格指定のない求人は「中立」として配点の 50%

**背景**: 資格 10 点の配点で、求人側に必要資格の指定がない場合の扱いが未定義だった。

**判断**: 満点でも 0 点でもなく、配点の 50% を与える。

**理由**: 満点にすると資格を持たない候補者が不当に有利になり、0 点にすると資格保有者が不当に不利になる。どちらも「資格が要件でない求人」の実態を表さない。

---

## ADR-008: 業界経験は「近接業界」を 50% 評価

**背景**: 業界経験 10 点の判定で、完全一致以外の扱いが未定義だった。

**判断**: 化学メーカー / 重工業 / プラントエンジニアリング / 半導体 / 機械メーカー / 電機メーカー / 素材メーカー / 自動車部品 / 食品メーカーを相互に「近接業界」とし、50% を配点する。

**理由**: 設備保全・生産技術・施工管理といった職種では、製造業内での業界間転用が実際に成立している。完全一致のみを評価すると、成約可能性のある求人が下位に沈む。

**変更方法**: `src/lib/domain/matching.ts` の `adjacent` 配列を編集する。

## ADR-009: スキル・資格の正規化は最長一致

**背景**: 表記ゆれの正規化方式が未定義だった。

**判断**: 別名辞書との照合で**最も長く一致した**エントリを採用する。

**理由**: 単純な先勝ちだと、「予防保全」が「設備保全」の別名「保全」に部分一致して誤って丸められた（実際に発生した）。最長一致にすることで「予防保全」は「予防保全」のまま、「設備管理」は「設備保全」へ正しく寄る。

## ADR-010: 発見企業の所在地は判明時のみ記録する

**背景**: WEB 調査で発見した企業の所在地をどう決めるかが未定義だった。

**判断**: 検索結果から確実に読み取れた場合のみ設定し、不明な場合は空のままにする。候補者の希望勤務地で代用しない。

**理由**: 当初は候補者の希望エリアを企業所在地として保存していたが、埼玉県の企業が「大阪府」と記録され、営業文面にも誤った地名が出た。企業マスタに推測値を入れると、後続の判断すべてが誤情報の上に乗る。

## ADR-011: 開拓理由の職種は「最頻値」で決める

**背景**: 企業が主にどの職種を採用しているかの判定方法が未定義だった。

**判断**: 最新 1 件ではなく、その企業の WEB 求人と保有求人すべてから**最頻の職種**を採る。

**理由**: 最新 1 件で判定すると、直近に WEB 調査した候補者の職種にすべての企業が引きずられ、全社が同じ職種として表示された。営業文面の切り口も、この最頻職種に一致する求人を優先して引用する。

## ADR-012: 「マッチする候補者」の閾値は Match 60

**背景**: Business Development Score の「保有候補者との相性」で、何点以上をマッチとみなすかが未定義だった。

**判断**: Match Score 60 以上をマッチとみなし、8 名で満点とする。

**理由**: 60 点は「主要素のいくつかが合致し、提案の余地がある」水準。8 名は、単発求人ではなく継続的な採用支援先として見込める規模の目安。

**変更方法**: `src/lib/agents/business-development.ts` の `MATCH_THRESHOLD`。配点自体は管理画面から変更できる。

---

## ADR-013: 「その他」5 点の使い道

**背景**: マッチングスコアの「その他 5 点」の中身が未定義だった。

**判断**: 歓迎スキルの一致度と、求人がリーダー・PM 職の場合のマネジメント経験に配点する。

**理由**: 必須スキル（20 点）と切り分けることで、「必須は満たすが歓迎条件も満たす」候補者を上位に出せる。

---

## ADR-014: 期日のない状態を作らない

**背景**: CA が「候補者返信待ち」「検討中」と回答した場合、次回アクション日が決まらないことがある。

**判断**: 「候補者返信待ち」「求人検討中」「連絡予定」で日付が読み取れない場合、**2 営業日後**を再確認日として自動設定する。

**理由**: 期日のないタスクは監視対象から外れ、放置される。本システムの目的は放置の防止であるため、必ず次の期日を置く。

**関連**: 保留フェーズでは、次回接触予定日が未設定であること自体をアラートにしている。

## ADR-015: WEB 情報の鮮度は 30 日

**背景**: WEB 求人情報の「最終確認日」は必須とされていたが、いつ古いとみなすかは未定義だった。

**判断**: 最終確認から 30 日を超えたものを `stale` とし、Business Development Score の「現在の採用需要」も鮮度で減衰させる（14 日以内=100% / 30 日以内=70% / 60 日以内=40% / それ以降=10%）。

**理由**: 求人の募集終了は公開情報からは分かりにくい。古い情報を根拠に営業すると信用を損なう。

## ADR-016: 通知は宛先ごとに 1 通ずつ送る

**背景**: 経営者が複数いる場合の通知方法が未定義だった。

**判断**: 一斉配信（BCC）ではなく、宛先ごとに個別に送信し、`notification_logs` にも 1 件ずつ記録する。

**理由**: 誰に届いたかを監査可能にするため。また、将来 Slack DM 等の個人宛チャネルへ切り替えても同じ構造で動く。

---

## ADR-017: Agent は同期実行

**背景**: 実行方式（キュー・非同期ジョブ）が未定義だった。

**判断**: 画面からの手動実行・定期実行のいずれも同期実行とし、ジョブキューは導入していない。実行結果は `job_run_logs` に記録する。

**理由**: 現在の規模（候補者数百名程度）では数秒〜数十秒で完了し、キュー導入の複雑さに見合わない。

**将来**: 候補者数が増え、WEB 調査の対象が広がった場合はキュー（BullMQ / pg-boss 等）を導入する。`runJob()` の呼び出しをキュー投入に置き換えるだけで対応できる構造にしてある。

---

## ADR-018: 定期実行の時刻は設定値として持ち、スケジューラ自体は持たない

**背景**: 「定期処理の時刻は管理画面から変更可能にする」とされていた。

**判断**: 管理画面で時刻を設定・保存できるようにし、実行そのものは外部スケジューラ（cron / Vercel Cron / cloud scheduler）から `POST /api/cron/{job}` または `npm run agents:run {job}` を叩く方式にした。

**理由**: アプリケーションプロセス内にスケジューラを持つと、複数インスタンス構成で多重実行される。設定値は「スケジューラ側へ反映すべき値の管理場所」として機能する。

**運用**: 設定変更時は、スケジューラ側の cron 式も合わせて更新する。
