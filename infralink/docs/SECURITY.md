# セキュリティと個人情報保護

## 1. 最重要方針

本システムは候補者の職務経歴・年収・連絡先という機微な個人情報を扱う。以下は実装上の制約として組み込んであり、運用ルールではない。

1. **WEB 検索 Agent へ直接識別情報を渡さない**
2. **企業向け営業文面に候補者個人を特定できる情報を含めない**
3. **企業への情報開示には本人同意フラグを必須とする**
4. **企業からの見送り理由の原文は改変・削除しない**
5. **AI が重要情報を勝手に確定しない**

## 2. 個人情報の外部送信

### 2.1 匿名化

Market Research Agent は候補者レコードを直接使わない。必ず `anonymizeProfile()` を通した匿名プロフィールのみを使う。

```
入力: 山田 太郎 / yamada.taro@example.com / 090-0000-0001 / 大阪府大阪市北区○○1-2-3 / 34歳 / 設備保全8年
   ↓ anonymizeProfile()
出力: 34歳 / 大阪府 / 化学メーカー / 設備保全8年 / PLC / シーケンス制御 / 電験三種
```

- 氏名・メール・電話番号は含めない
- 住所は `coarseLocation()` で**都道府県まで**に丸める（市区町村以下を落とす）

### 2.2 送信前の検証

匿名化したつもりで漏れることを防ぐため、検索クエリの組み立て後・送信前に検査する。

```typescript
assertNoDirectIdentifiers(queryText, 'WEB 検索クエリ');
if (profile.name && queryText.includes(profile.name)) {
  throw new Error('個人情報保護違反の可能性: 検索クエリに候補者氏名が含まれています');
}
```

検査対象パターン: メールアドレス / 電話番号 / 「N丁目」/ 「N-N-N」形式の番地。

**違反を検知した場合は例外を投げて処理を停止する。** 警告を出して続行はしない。

実装: `src/lib/domain/anonymize.ts`

### 2.3 営業文面

Business Development Agent が生成する営業メッセージ案は、

- `stripNames()` でマッチした候補者全員の氏名を除去する
- 記載する人数は「6 名」のような集計値のみ
- 経験領域・保有資格・希望条件は**匿名の概要として**のみ記載する
- エリアは企業所在地ではなくマッチした候補者の居住地の最頻値から出す（事実と異なる記載を避けるため）

### 2.4 情報開示の同意

`candidates.disclosure_consent` が本人同意フラグ。将来、企業へ候補者情報を開示する機能を追加する場合は、このフラグが `true` であることを必須条件とする。候補者詳細画面では未同意の場合に警告を表示する。

## 3. 認証

| 項目 | 実装 |
| --- | --- |
| パスワード | bcrypt（cost 10）でハッシュ化。平文は一切保持しない |
| セッション | HMAC-SHA256 署名付き JWT（`jose`） |
| Cookie | `httpOnly` / `sameSite=lax` / 本番は `secure` |
| 有効期限 | `SESSION_MAX_AGE_HOURS`（既定 12 時間） |
| 署名鍵 | `AUTH_SECRET`（32 文字以上。未設定・短すぎる場合は起動時に例外） |

セッション検証時は JWT の署名確認に加えて **毎回 DB を参照**する。これにより、利用者を無効化（`active=false`）した時点で既存セッションも失効する。

ログイン失敗時は「アカウントが存在しない」と「パスワードが違う」を区別しないメッセージを返す（アカウント列挙の防止）。

### 本番導入前に必ず行うこと

- [ ] `AUTH_SECRET` をランダムな長い文字列に変更（`openssl rand -base64 48`）
- [ ] デモユーザーの削除、または全パスワードの変更（初期値は `infralink2026`）
- [ ] `CRON_SECRET` の設定
- [ ] HTTPS 経由でのみ提供する
- [ ] `.env` を配布物・リポジトリに含めない

## 4. 権限

`src/lib/rbac.ts` で「ロール → 権限集合」として定義する。画面はロールを直接参照せず `can()` を通すため、将来の細分化が容易である。

| 権限 | admin | executive | CA | RA |
| --- | :-: | :-: | :-: | :-: |
| `candidate:read_all` | ● | ● | ● | ● |
| `candidate:write` | ● | | ● | |
| `company:read` / `job:read` | ● | ● | ● | ● |
| `company:write` / `job:write` | ● | | | ● |
| `bd:read` | ● | ● | | ● |
| `bd:write` | ● | | | ● |
| `alert:read_all` | ● | ● | | |
| `alert:read_own` | ● | | ● | |
| `report:read` | ● | ● | ● | ● |
| `settings:write` | ● | ● | | |
| `user:manage` | ● | | | |
| `audit:read` | ● | ● | | |

- CA は既定で**自分の担当候補者**に絞り込まれる（`defaultCandidateScope()`）。アラートも自分宛のみ表示される。
- CA が回答できる AI 確認は**自分宛のアラートのみ**（`respondToAlertAction` で検証）。
- 権限がない画面はエラーではなく専用の 403 表示になる。
- Server Action 側は `assertCan()` で例外を投げる（画面の表示制御だけに頼らない）。

## 5. 監査ログ

誰が・いつ・どの情報を・どう変更したかを `audit_logs` に記録する。

| `actor_type` | 意味 |
| --- | --- |
| `human` | 利用者による操作（`actor_id` に users.id） |
| `AI` | Agent による自動更新（`actor_label` に Agent 名） |
| `system` | 同期処理など |

記録対象: 候補者情報の更新、フェーズ変更、アラートの生成・解消・エスカレーション、見送り理由タグの確定、営業進捗の更新、設定変更、ログイン、データ同期。

変更前後の値を JSON で保持する。通知の送信履歴は `notification_logs` に、定期ジョブの実行履歴は `job_run_logs` に別途残る。

## 6. AI による自動更新の境界

| AI が自動更新してよい | 人の確認が必要 |
| --- | --- |
| AI タグ / スキル抽出 | 選考辞退 |
| 推奨求人・マッチングスコア | 転職活動終了 |
| WEB 調査結果 | 年収希望の変更 |
| アラート生成 | 企業への候補者推薦 |
| 次回アクションの提案 | 個人情報の開示 |
| 見送り理由タグの**提案** | 見送り理由タグの**確定** |
| 新規開拓スコア | 営業進捗・担当 RA |

実装上の担保:

- 同期で取り込んだスキル・資格は `source='human'` となり、AI 抽出（`source='ai'`）が上書きしない
- フェーズ変更は画面からの明示操作（`updatePhaseAction`）のみ
- 見送り理由タグは `rejection_tag_confirmed_by` が入るまで「AI 提案（人による確定待ち）」と表示される
- 営業進捗と担当 RA は Agent の再実行で上書きされない

## 7. 秘密情報の管理

- API キー・パスワード・秘密鍵をコードに書かない。すべて環境変数（`.env`）で管理する
- `.env` は `.gitignore` 済み。`.env.example` のみコミットする
- Google サービスアカウントの秘密鍵は環境変数に格納し、鍵ファイルをリポジトリに置かない
- `/api/cron/*` は `CRON_SECRET` による Bearer 認証。未設定時、本番環境では 401 を返す

## 8. 入力検証

Server Action の入力は `zod` で検証する。列挙値（フェーズ・見送り理由タグ・営業進捗）はホワイトリストで確認し、不正な値は拒否する。

データベースアクセスは Prisma 経由のみで、SQL を文字列連結で組み立てない。

## 9. 外部 API 障害時の挙動

各 Adapter は障害時に Mock へフォールバックし、業務を止めない。ただし**フォールバックしたことを隠さない**。

- 管理画面の「接続状態」に Mock 使用中と表示する
- 同期結果に警告を返す
- LLM がフォールバックした場合は `degraded=true` となり、ルールベースの結果が使われる（Confidence が `Low` になる）
