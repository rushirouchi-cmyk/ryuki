# プロンプト設計方針

## 全サブエージェント共通のシステムプロンプト骨格

各サブエージェントのシステムプロンプトは次の 5 セクションで構成する。

```
1. あなたの役割      — 一言でこのエージェントが何者か
2. 入力              — どのフィールド・ツール結果を受け取るか
3. 出力              — 何をどの形式で返すか (JSON / Markdown)
4. 使ってよいツール   — 明示的なホワイトリスト
5. 禁則               — 送信禁止・PII 出力禁止・断定禁止など
```

「禁則」を必ず持たせるのがポイント。曖昧さは事故を招く。

## テンプレート配置

```
prompts/
├── orchestrator.md
├── jd_author.md
├── scout_writer.md
├── sourcing.md         # v2
├── scheduler.md        # v2
└── pipeline_analyst.md
```

各ファイルには次のブロックを含める。

- `## system` — サブエージェントのシステムプロンプト本体
- `## few_shots` — 3〜5 件の入出力例
- `## anti_examples` — やってはいけない出力例と、その理由

## 各エージェントの重要事項

### JD Author
- **敬体・トーンは会社カルチャーに合わせる**。カルチャーガイド (Google Drive の指定文書) を毎回参照させる。
- **数値の捏造禁止**。給与レンジ・従業員数・売上などは、入力で与えられなければ「(要記入)」と明示する。

### Scout Writer
- **氏名は `{{candidate_name}}` プレースホルダで固定**。実名は絶対に生成しない。
- **媒体別の文字数上限を厳守**:
  - Wantedly スカウト: 700 文字
  - BizReach プラチナスカウト: 3,000 文字
  - LinkedIn InMail: 1,900 文字
- **開幕 3 行以内に「あなたに送っている理由」を書く**。テンプレ感を出さない。
- **A/B 2 案** を必ず返す (件名 × 本文の組合せ)。

### Pipeline Analyst
- **TL;DR を最初に**。3 文以内。数値と傾向。
- **前週比・前月比は指標名の直後に必ず添える**。単独の数値だけ出さない。
- **アラートは「事実 → 仮説 → 提案」の順**。仮説と事実を混ぜない。

### Orchestrator
- **迷ったら聞き返す**。曖昧な依頼を勝手にサブエージェントに丸投げしない。
- **サブエージェントの結果を要約せず、そのまま提示する**。二次加工でニュアンスが変わることを避ける。

## Few-shot 例の書き方

- 実データを使わない。全て架空の会社・氏名 (`山田太郎` などのダミー) にする。
- 「良い出力」と「そこそこの出力」を並べる。両者の違いを短くコメント。

## Anti-examples の例 (Scout Writer)

```
❌ 悪い例:
「田中太郎様、突然のご連絡失礼いたします。弊社は AI を活用した SaaS プロダクトを展開しており…」

理由: 
- 実名 (「田中太郎」) を LLM が生成している → プレースホルダ違反
- 冒頭が自社紹介 → 候補者視点が不在
- 「あなたに送っている理由」が 3 行以内にない
```

## プロンプト運用

- 変更は PR ベースで review。過去バージョンとの diff が読める形にする。
- 本番投入前に、代表 5 ケースで A/B 比較を回す。
- 3 ヶ月に 1 回、実データ (匿名化済み) でリグレッション検査を行う。
